# V1 Detailed Summary

> This is the fullest **product/feature** narrative for V1. The architecture
> below was refreshed for the Phase 4 FastAPI cutover (#38, #244): FastAPI
> ([apps/api/](../apps/api/)) is now the sole JSON API, and the Next `/api/*`
> data routes plus the Next JWT/`session`-cookie auth stack have been removed.
> For the authoritative architecture, see [API_BACKEND_MIGRATION_PLAN.md](API_BACKEND_MIGRATION_PLAN.md)
> and the root [CLAUDE.md](../CLAUDE.md), which this doc defers to.

## Product & Feature Summary

- **Single-family private space:** V1 targets one household; every member creates their own login and joins the sole `FamilySpace` with a shared master key. The app’s job is equal parts preservation (recipes that last) and social fun (lightweight posts, reactions, and cooked logs).
- **Auth + Family Master Key:** Signup requires name, email/username, password, and the master key hashed in `FamilySpace.masterKeyHash`; the first successful signup becomes `owner`, everyone else is `member`. The Next auth routes (`src/app/api/auth/signup/route.ts`, `src/app/api/auth/login/route.ts`) are thin same-origin proxies that forward to FastAPI `/v1/auth/*`; FastAPI sets the HTTP-only `refresh_token` + `csrf_token` cookies, and the middleware (`src/proxy.ts`) redirects unauthenticated traffic to `/login`.
- **Timeline:** `/timeline` server-renders its first page from `getTimelineFeed` (`src/lib/timeline-data.ts`); `TimelineFeed` (`src/components/timeline/TimelineFeed.tsx`) then paginates against the FastAPI timeline endpoint (`/v1/timeline`). The feed includes posts, comments, cooked events, reactions, and post edits with change notes, each rendered via `TimelineCard`.
- **Posts & Recipes:** Users can add quick posts or expand into recipes from `/add` using `AddPostForm` (`src/components/add/AddPostForm.tsx`). Photos (up to 10) are optional; recipe metadata (origin, ingredients, steps, time, servings, courses, difficulty, tags) is only persisted when both ingredients and steps are provided.
- **Recipe details & browsing:** Structured recipes show ingredient/step blocks, metadata chips, and edit history in `PostDetailView` (`src/components/post/PostDetailView.tsx`). `/recipes` loads `RecipesBrowseClient`, letting users search by title, filter by course/tags/difficulty/author, constrain cook time & servings, and add up to five ingredient keywords; results come from the FastAPI recipes endpoint (`/v1/recipes`), with the first page server-rendered via `getRecipes` (`src/lib/recipes.ts`).
- **Comments & reactions:** Post detail includes flat comments with optional photo attachments and emoji reactions on both posts and comments. Handlers live in the FastAPI routers `apps/api/src/routers/v1/comments.py` (`/v1/posts/{postId}/comments`) and `apps/api/src/routers/v1/reactions.py` (`/v1/reactions`).
- **“Cooked this” events & ratings:** The cook modal inside `PostDetailView` hits `/v1/posts/{postId}/cooked` (`apps/api/src/routers/v1/posts.py`), storing a `CookedEvent` with optional 1–5 rating and note. Aggregated stats (times cooked, avg rating) update immediately and the recent cooks list is paginated.
- **Favorites:** Users can toggle favorites from post detail via `/v1/posts/{postId}/favorite`; `/profile` tabs read `/v1/me/favorites` to show the private list.
- **Profiles & family members:** `/profile` shows My Posts, Cooked, and Favorites tabs with lazy pagination. `/family-members` surfaces everyone in the family space, and owners/admins can remove members via `/v1/family/members/{userId}` while the master key remains the gate for new joiners.

## Technical Architecture

- **Next.js App Router + TypeScript (UI + SSR):** Pages under `src/app/(auth)` handle entry, while the authenticated app lives under `src/app/(app)` with a shared layout that verifies the session against FastAPI (`/v1/auth/session`) before rendering. Server components fetch their initial data **directly from Postgres via Prisma** — the `src/lib/*` data modules (`timeline-data.ts`, `recipes.ts`, `posts.ts`, `profile.ts`, `family.ts`, `notifications.ts`) — while interactive flows are client components marked with `'use client'`.
- **FastAPI JSON API (the backend):** The Python service in [apps/api/](../apps/api/) is the sole JSON API. Its routers live under `apps/api/src/routers/v1/*.py` and are served under `/v1` (auth, posts, comments, reactions, recipes, me, profile, family, tags, timeline, notifications, feedback, health). Client components call it through `src/lib/apiClient.ts`, which attaches an in-memory Bearer access token and transparently refreshes-and-retries on 401. Input is validated with Pydantic schemas mirroring the original Zod contract. The former Next `src/app/api/**` data routes were removed in the Phase 4.3 cutover (#231); only the `auth/*` proxies, `auth/bootstrap`, and `health` remain under `src/app/api/`.
- **Prisma + Postgres:** `prisma/schema.postgres.node.prisma` (JS client) backs the Next runtime’s server-component reads and the Cloud Run Next image’s migrations; `prisma/schema.postgres.prisma` (Python client) backs FastAPI and Cloud SQL migrations. The two schemas are kept field-identical — see [prisma/CLAUDE.md](../prisma/CLAUDE.md). Both model the domain with future multi-family flexibility even though V1 seeds a single `FamilySpace`. The seed script (`prisma/seed.ts`) hashes an initial master key and loads the curated tag catalog.
- **Auth & sessions (FastAPI-owned):** FastAPI hashes credentials with bcrypt, signs JWT access + refresh tokens (PyJWT) with its own signing secret, and sets an HTTP-only **rotating** `refresh_token` cookie plus a `csrf_token` double-submit cookie. The browser never holds a long-lived Next-signed session; instead the client mints a short-lived in-memory access token on each page load via `/api/auth/bootstrap` (which proxies FastAPI `/v1/auth/refresh` + `/v1/auth/me`) and keeps it in `src/lib/authStore.ts`. The Next middleware (`src/proxy.ts`) gates the `(app)` group with a presence-only `refresh_token` check (`hasRefreshTokenFromRequest` in `src/lib/session-core.ts`); SSR pages resolve the user via `resolvePageUser` (`src/lib/session.ts`) → FastAPI `/v1/auth/session`.
- **File uploads:** Photos are stored under opaque `storageKey` values (never URLs). FastAPI writes new uploads to GCS in production — and to local disk in dev — via `apps/api/src/uploads.py`; the DB row stores only the key. A signed, time-limited URL is resolved at response/render time — server components use `src/lib/uploads.ts` (`getSignedUploadUrl` / `createSignedUrlResolver`). MIME type (JPEG/PNG/WEBP/GIF) and a size cap are enforced on write, and removing a post deletes its linked objects.
- **Environment & secrets:** `.env` must provide `DATABASE_URL`. The token-signing secret now lives on the **FastAPI** service, not the Next app — the Next service no longer signs anything (`JWT_SECRET` was removed from it in #243). The master key hash lives in the DB and should be reseeded per family. No secrets are baked into the client.
- **UI foundation:** Styling leans on Tailwind classes defined in `src/app/globals.css`. Mobile-first layouts use cards, rounded containers, and a persistent bottom nav (`src/components/navigation/BottomNav.tsx`).

## Domain Model & Data Structures

- **User / FamilySpace / FamilyMembership:** Users (`users` table) store profile basics and password hash. They belong to a `FamilySpace` via `FamilyMembership` (role `owner|admin|member`). V1 assumes one family but the schema supports multiple rows.
- **Post:** Represents every timeline entry. Key fields (`title`, `caption`, `mainPhotoUrl`, `hasRecipeDetails`, `lastEditedBy`, `lastEditNote`, `lastEditAt`) allow lightweight posts plus tracked recipe edits.
- **PostPhoto:** Ordered gallery images with `sortOrder`, enabling drag-ish ordering in `AddPostForm` and deterministic cover selection.
- **RecipeDetails:** Optional 1:1 with Post storing origin, serialized JSON arrays for `ingredients` and `steps`, numeric `totalTime` (minutes) and `servings`, primary course(s), and difficulty. Courses are stored both as a single `course` and a JSON `courses` array to support multi-select filters.
- **Tag / PostTag:** Seeded canonical tags (diet, allergen, heat, flavor, cuisine) linked via `PostTag`. Tags are required to come from the curated set.
- **Comment:** Flat comments with optional `photoUrl`; includes `deletedAt` for soft deletes, though current handlers hard-delete.
- **Reaction:** Stores per-user emoji reactions for posts or comments with a uniqueness constraint on `(targetType, targetId, userId, emoji)` and redundant post/comment FKs for fast joins.
- **CookedEvent:** Logs “Cooked this” actions with optional rating and note; stats are computed via aggregates rather than stored columns.
- **Favorite:** User-private bookmarks (unique `(userId, postId)`), powering the profile favorites tab.
- **Enums & helpers:** Course and difficulty enums live in `src/lib/validation.ts`. Ingredient units (tsp, tbsp, unitless, etc.) are enumerated and formatted via `src/lib/ingredients.ts`.

## Implementation Details of Core Flows

- **Signup & master key enforcement:** `POST /v1/auth/signup` (proxied by `src/app/api/auth/signup/route.ts`) validates the payload, ensures the master key matches the hashed value in `FamilySpace`, promotes the very first member to `owner`, and writes both `User` and `FamilyMembership` inside a transaction. FastAPI returns an access token and sets the rotating `refresh_token` cookie, honoring a longer TTL when “Remember me” is checked.
- **Login & session management:** `POST /v1/auth/login` (proxied by `src/app/api/auth/login/route.ts`) finds the user, verifies the bcrypt hash, ensures at least one membership, and issues the access token plus `refresh_token`/`csrf_token` cookies. `proxy.ts` vets auth for `/timeline`, `/recipes`, `/add`, `/profile`, `/family-members`, `/notifications`, and `/posts`, redirecting anonymous users to `/login?redirect=…`.
- **Creating posts & recipes:** `AddPostForm` builds a `FormData` payload (a JSON `payload` plus photo files), normalized via `normalizePostPayload` (`src/lib/postPayload.ts`) so recipe details persist only when both ingredients and steps survive validation, then sends it through `apiClient` to `POST /v1/posts` (`apps/api/src/routers/v1/posts.py`). That handler saves photos, enforces the photo-count cap, creates `PostPhoto` rows with sort order, connects approved tags, and writes `RecipeDetails` with serialized ingredient/step arrays. Quick posts skip the recipe block entirely.
- **Editing posts, change notes, and tags:** `PUT /v1/posts/{postId}` revalidates permissions (author or owner/admin), parses a `photoOrder` array so users can mix existing and new uploads, enforces distinct ordering, and deletes removed photos from both DB and storage. Recipe details are upserted or removed depending on payload, tags are rewritten, and `lastEditedBy`, `lastEditNote`, `lastEditAt` capture revision metadata. The detail page (`src/app/(app)/posts/[postId]/page.tsx`) server-renders via `getPostDetail` (`src/lib/posts.ts`), and `PostDetailView` surfaces the edit info and an optional change-note ribbon.
- **Uploading & associating photos:** FastAPI writes new photos under opaque storage keys (`apps/api/src/uploads.py`); create/edit set the cover (`mainPhotoUrl`, which holds a storage key) to the first ordered photo, and comment attachments reuse the same path. The delete route cleans up all linked objects. Signed URLs are resolved only at read time (`src/lib/uploads.ts` for SSR).
- **Timeline aggregation:** `getTimelineFeed` (`src/lib/timeline-data.ts`, used by the SSR page) and the FastAPI `/v1/timeline` endpoint (`apps/api/src/routers/v1/timeline.py`, used for pagination) each fetch recent posts, comments, reactions (post targets), cooked events, and edits, normalize them into timeline items, sort by timestamp, and slice by `limit/offset`. There is no precomputed `TimelineEvent` table; the union query runs per request and is acceptable for the small single-family scale.
- **“Cooked this” logging & stats:** `POST /v1/posts/{postId}/cooked` validates rating (1–5) and optional note, guards access to the family space, inserts a `CookedEvent`, and returns updated aggregates plus a paginated recent history; `GET /v1/posts/{postId}/cooked` serves subsequent pages. Front-end state reuses those payloads for optimistic refreshes.
- **Favorites & profile surfaces:** Favorite toggles hit `POST`/`DELETE /v1/posts/{postId}/favorite`. Profile tabs page through the FastAPI profile endpoints and `/v1/me/favorites`; `profile/page.tsx` prefetches the first page server-side (`src/lib/profile.ts`) so the UI renders immediately, then client-side “Load more” buttons fetch subsequent pages via `apiClient`.
- **Family management:** The `/family-members` server component fetches members via `getFamilyMembers` (`src/lib/family.ts`) — role, join date, post count. The client component lets owners/admins invoke `DELETE /v1/family/members/{userId}`, which in turn blocks removing yourself or the owner.
- **Comments & reactions:** Comment creation posts multipart FormData to `POST /v1/posts/{postId}/comments` (optional photo upload); `PostDetailView` then offers reaction buttons per comment. Reactions toggle through `/v1/reactions`, which inserts or deletes the record and rebuilds the summary list shown in the UI. Both are served by `apps/api/src/routers/v1/comments.py` and `apps/api/src/routers/v1/reactions.py`.

## Current State, Gaps & Limitations

- **End-to-end coverage:** Auth, timeline, post CRUD (including recipes, tags, photos), comments, reactions, cooked events, favorites, recipe search, profile tabs, and family-member management are implemented — the FastAPI service owns the JSON API and Next server components own SSR reads. The UI matches the mobile-first wireframes and uses client components only where interactivity is needed. Coverage is exercised by Jest (unit/integration), Playwright (`@smoke`), and FastAPI `pytest` suites.
- **Known gaps / TODOs:**
  - No true soft-delete for comments despite a `deletedAt` column; deletes are permanent.
  - Timeline aggregation performs several separate queries per request with no caching; fine for V1 but could be slow with larger histories.
  - Rate limiting is in-process in FastAPI (`apps/api/src/rate_limit.py`) — the Next-side `src/lib/rateLimit.ts` has had no consumers since #231 deleted the `/api/*` data routes. Limiter state is per-instance, so a multi-instance deploy would not share it — acceptable for the current single-instance Cloud Run setup (shared storage tracked in #33).
  - Multi-family tenancy, invitations, public sharing, meal planning, etc., remain out of scope per the product spec.
- **Configuration assumptions:** The seed script prints a generated master key on first run — save it and rotate before real usage. `.env` needs strong secrets, and deployment should use HTTPS so the `refresh_token`/`csrf_token` cookie settings (`httpOnly`, `sameSite`, `secure` in production) deliver the intended protection.
